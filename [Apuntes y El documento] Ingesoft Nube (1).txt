
2. Sistema de software
* CocoCash
  

* CocoCash se propone como una billetera digital nativa de la nube, diseñada para simular transferencias monetarias entre usuarios en un entorno seguro y escalable. El sistema permite al usuario registrarse y autenticarse, crear automáticamente su billetera, manejar su saldo, transferir dinero a otros usuarios y consultar el historial de movimientos. La arquitectura combina microservicios con arquitectura basada en eventos, y aprovecha los servicios de nube de: base de datos relacional administrada, notificación y publicación-suscripción, monitoreo y observabilidad; y gestión de claves criptográficas.

Protocolo: HTTP/REST(JSON).

	Compute: AWS Lambda.
Lenguaje: Go.
Integración: AWS SDK. Protocolo: HTTPS (invocación interna).
	cococash-pdf-maker (generador de reportes)
	Consumir eventos con información de transacciones. Generar documentos PDF con el resumen mensual de transacciones de cada usuario. Almacenar los archivos generados en almacenamiento de objetos.
	Compute: AWS Lambda.
Lenguaje: Go.

	cococash-pdf-odb (almacenamiento de objetos)
	Almacenar archivos PDF generados con los reportes de transacciones. Proveer acceso a objetos mediante enlaces firmados temporales. Encargado del ciclo de vida de los objetos.
	Servicio: Amazon S3.
Paradigma: Object Storage.
Protocolo: HTTPS (S3 REST API).
	cococash-link-generator (servicio de generación de enlaces)
	Generar URLs firmadas temporales para acceder a los reportes almacenados en el almacenamiento de objetos. Controlar el acceso a los documentos generados.
	Compute: AWS Lambda.
Lenguaje: Go.
Integración: AWS SDK (S3).

3.1.2.2. Descripción de los elementos
Componente
	Responsabilidad y atributos
	Servicios de nube usados y configuración básica
	Anotaciones
	cococash-wfe (Frontend)
	Disponibilidad y performance: provee la interfaz web del sistema y gestiona la interacción con los usuarios finales. Se despliega como aplicación web independiente para servir contenido dinámico y estático. Permite escalar horizontalmente durante picos de tráfico gracias a su despliegue en Fargate. No tiene lógica de servidor SSR. La única lógica que contiene es la necesaria para estar disponible para entrega de archivos.


	Hosting web moderno (React.js).
Integración mediante HTTP/REST hacia Amazon API Gateway. Se despliega como contenedor en lugar de almacenamiento estático para mantener consistencia operativa con el resto de servicios, permitir mayor control sobre seguridad y routing mediante un servidor web, y facilitar portabilidad entre entornos cloud.


	Todos los Fargates están en el mismo clúster.
	cococash-ag (API Gateway)
	Seguridad y control de tráfico: centraliza la autenticación mediante JWT y gestiona el enrutamiento de solicitudes hacia los microservicios internos. También hace protección de rutas mediante el JWT (el usuario no puede acceder directamente a una ruta protegida por JWT).
Protege contra ataques DoS mediante el throttling por defecto de AWS y desacopla el frontend de los servicios backend.
	Amazon API Gateway: - Tipo: REST API. Auth: Cognito User Pool Authorizer. Throttling: 1000 req/sec (Burst: 2000). Integración HTTP hacia servicios backend (wallet-ms, transaction-ms, link-generator).
	Este es un servicio gestionado desde el proveedor de nube, no cuenta con lógica propia (código escrito por el equipo).
	cococash-auth-ms (identidad)
	Delega la autenticación y gestión de usuarios a un servicio especializado. Permite registro, autenticación y emisión de tokens JWT. Facilita integración segura con API Gateway.
	Amazon Cognito: User Pool configurado con MFA. Emisión de tokens JWT (ID Token, Access Token, Refresh Token). Políticas de contraseña seguras.
	Igual que el componente anterior, este es implementado mediante un SaaS.
	cococash-wallet-ms (core)
	Consistencia y baja latencia: gestiona la lógica transaccional del sistema (cuentas y transferencias). Su despliegue en un clúster de contenedores serverless permite escalar dinámicamente según la carga y mantener alta disponibilidad en múltiples zonas.
	AWS ECS (Fargate): Service con Application Load Balancer. Task Definition: 1 vCPU / 2GB RAM. Despliegue en Private Subnet 1. Permisos IAM para publicar eventos en SNS.
	

	cococash-transaction-ms (auditoría)
	Procesamiento de eventos y auditoría: consume eventos de transferencias desde el bus de eventos y registra entradas inmutables en el historial de transacciones. Su ejecución continua permite procesar flujos de eventos sin latencia de inicialización.
Sirve los registros de las transacciones, que el usuario puede consultar desde el frontend. Estos registros también se usan en la fabricación de los certificados.
	AWS ECS (Fargate): Runtime: Go. Task Definition: 0.25 vCPU / 0.5GB RAM. - Worker consumiendo y produciendo mensajes de SQS. - IAM Role para escritura en DynamoDB, lectura/borrado en SQS y escritura en SNS (para envío de eventos).
	

	cococash-event-bus (bus de eventos)
	Desacoplamiento y resiliencia: permite que wallet-ms publique eventos de dominio sin depender de la disponibilidad de otros servicios. Garantiza entrega confiable y reintentos automáticos mediante colas persistentes.
Coordinación de procesos batch: permite distribuir eventos relacionados con generación de reportes mensuales y procesamiento de transacciones históricas. Facilita pipelines asincrónicos para generación de documentos.
	Amazon SNS + SQS: SNS Topics de dos tipos: de transferencias y de generación de reportes.
SQS queues con DLQ para reintentos. Retención de mensajes de 4 a 14 días.


	Es el orquestador asincrónico para todo el sistema.
Se compone de un servicio de mensajes SNS y varias colas SQS hacia los suscriptores.
	cococash-trigger (scheduler)
	Automatización de procesos periódicos: activa el flujo de generación de reportes mensuales el primer día de cada mes. Dispara funciones serverless sin necesidad de infraestructura dedicada.
	Amazon EventBridge: Rule programada (cron mensual).
Invocación directa de Lambda (get-accounts).
	Este componente no tiene lógica.
	cococash-get-accounts (consultor de cuentas)
	Orquestación inicial del pipeline de reportes: consulta la lista de cuentas bancarias (todas, tanto activas como inactivas) y publica eventos en lotes para iniciar la generación de reportes por cuenta.
	AWS Lambda: Runtime Go. Invocada por EventBridge. consulta cuentas bancarias desde wallet-ms enrutando por cococash-ag y publicar en SNS.
	Se escogió Go para la implementación debido a que es compilado (más rápido de ejecutar), optimiza costos.
	cococash-pdf-maker (generador de reportes)
	Procesamiento serverless de reportes: consume eventos con información de transacciones y genera documentos PDF con el resumen mensual de movimientos de cada usuario y los almacena en S3.
	AWS Lambda: Runtime Go. - Librerías de generación de PDF. Integración con S3 mediante AWS SDK.
	

	cococash-link-generator (generador de enlaces)
	Seguridad de acceso a documentos: genera enlaces firmados temporales que permiten descargar reportes almacenados en S3 sin exponer directamente el bucket.
	AWS Lambda: Runtime Go Generación de Signed URLs mediante AWS SDK. Invocación vía API Gateway.
	

	cococash-wallet-db (saldos)
	Integridad de datos financieros: almacena balances actuales y estado de transferencias. Garantiza propiedades ACID para asegurar consistencia en operaciones financieras.
	Amazon RDS (PostgreSQL): - Instancia: db.t3.micro. - Multi-AZ habilitado. - Storage: gp3 con auto-escalado.
	Esta base de datos está en la zona de disponibilidad: az1 con fallback stand-by en az2.


	cococash-transaction-db (historial)
	Escalabilidad y consultas de auditoría: almacena el historial completo de transacciones. Permite consultas rápidas por usuario y rango temporal.
	Amazon DynamoDB: Capacity Mode: On-demand. Partition Key: user_id.
Sort Key: timestamp.
	Esta base de datos se implementa en el servicio Amazon DynamoDB, diseñado para la nube.
	cococash-pdf-odb (almacenamiento de documentos)
	Persistencia de reportes generados: almacena archivos PDF generados con los estados de cuenta mensuales de los usuarios. Permite acceso mediante URLs firmadas temporales.
	Amazon S3: Bucket privado. Sin versionado. Acceso mediante Signed URLs generadas por Lambda.
	Reside en múltiples zonas de disponibilidad simultáneamente.

3.2.1.3. Base de datos de transacciones (log)

	Campo
	Tipo de Dato
	Restriction / Default
	Descripción
	user_id
	STRING
	PK (Partition Key), Not Null
	Identificador del usuario dueño del registro de transacción. Se usa como clave de partición para agrupar el historial de transacciones por usuario.
	timestamp
	STRING
	SK (Sort Key), Not Null
	Marca de tiempo asociada al evento o transacción. Permite ordenar cronológicamente las transacciones de un usuario.
	transaction_id
	STRING
	Not Null, GSI (transaction_id-index)
	Identificador único de la transacción. Se utiliza para consultas directas mediante un índice secundario global (GSI).

	STRING
	Nullable
	Identificador de la transferencia asociada cuando la transacción corresponde a un movimiento entre cuentas.

	STRING
	Not Null

	amount
	NUMBER (decimal)
	Not Null

	currency
	STRING (3)
	Not Null
	Código de moneda de la transacción según estándar ISO-4217 (ej. USD, COP, EUR).
	source_account_id
	STRING
	Nullable
	Identificador de la cuenta origen en una transferencia.
	destination_account_id
	STRING
	Nullable
	Identificador de la cuenta destino en una transferencia.
	status
	STRING
	Not Null
	Estado actual de la transacción (SUCCESS, FAILED, PENDING, etc.).
	description
	STRING / TEXT
	Nullable
	Descripción opcional o comentario asociado a la transacción.
	event_source
	STRING
	Not Null
	Servicio o componente del sistema que generó el evento registrado.
	event_type
	STRING
	Not Null
	Tipo de evento procesado que originó el registro (ej. TransferCreated, TransferCompleted).
	recorded_at
	STRING (timestamp)
	Not Null
	Fecha y hora en que el evento fue registrado en el sistema de auditoría.
	

transaction_type
transfer: Movimiento de dinero entre cuentas dentro del sistema.
deposit: Ingreso de dinero a una cuenta.
withdrawal: Retiro de dinero desde una cuenta.


Nota: El tipo de transacción indica la naturaleza del movimiento registrado en el sistema. En el caso de transferencias, la información de las cuentas involucradas se almacena en source_account_id y destination_account_id.


transaction_status
PENDING: La transacción ha sido registrada pero aún no ha finalizado su procesamiento.
SUCCESS: La transacción se procesó correctamente y el resultado fue aplicado en el sistema.
FAILED: La transacción no pudo completarse debido a un error o condición de negocio.

	3.2.3. Flujos funcionales (Usuario - GUI)
Usuario(s) del sistema: cliente.
  

Flujo 1: Registro e inicio de sesión del usuario
Objetivo: permitir al usuario acceder al sistema de manera autenticada.
1. El usuario accede a la aplicación y visualiza la pantalla de autenticación (Login).
2. Si el usuario no tiene una cuenta, selecciona la opción de registro.
3. El sistema presenta el formulario de registro.
4. El usuario completa y envía el formulario.
5. El sistema valida la información:
   1. Si el registro es exitoso, el sistema le envía un correo con un código de verificación.
   2. Si el registro falla, el sistema redirige al usuario nuevamente a la pantalla de Login.
6. El usuario digita el código de verificación y es redirigido a la pantalla de Login.
7. Un usuario ya registrado puede iniciar sesión directamente desde la pantalla de Login.
8. Una vez autenticado correctamente, el usuario accede al Dashboard.


Flujo 2:  Consulta de saldo
Objetivo: Permitir al usuario visualizar los fondos disponibles en su cuenta.
1. El usuario autenticado accede al Dashboard.
2. Una vez en el Dashboard, el sistema consulta y muestra el saldo disponible en la cuenta del usuario.


Flujo 3: Realización de una transferencia
Objetivo: permitir al usuario transferir dinero a otra cuenta.
1. Desde el Dashboard, el usuario selecciona la opción de transferencias (Módulo de transferencias).
2. El sistema presenta el formulario de transferencia.
3. El usuario ingresa los datos requeridos para la operación (monto a transferir y cuenta de destino como campos obligatorios, mensaje como campo opcional).
4. El sistema valida la información ingresada en el formulario:
   1. Si la información obligatoria no está completa, el sistema no inicia el procesamiento y redirecciona al módulo de transferencias para su corrección.
   2. Si la información está completa, el sistema inicia el procesamiento de la transferencia, donde se validan las reglas de negocio y consistencia de datos. En caso de detectarse errores (como fondos insuficientes o cuenta inválida), la operación se marca como fallida.
5. Una vez finalizado el procesamiento de la transferencia:
   1. El sistema actualiza el estado de la operación según el resultado (COMPLETED o FAILED).
   2. El usuario es redirigido al Dashboard, donde se muestra el resultado de la operación.
6. La transferencia queda registrada en el historial de movimientos, incluyendo su estado final y, en caso de fallo, el motivo correspondiente.


Flujo 4: Consulta de movimientos
Objetivo: permitir al usuario consultar su historial de transacciones.
1. Desde el Dashboard, el usuario selecciona la opción de consulta de movimientos.
2. El sistema muestra el historial de transacciones asociadas a la cuenta del usuario.
3. El usuario puede regresar al Dashboard para continuar utilizando el sistema.


Flujo 5: Consulta y descarga de extractos bancarios
Objetivo: permitir al usuario obtener el extracto mensual de su cuenta en formato PDF.
1. El usuario autenticado accede al Dashboard.
2. Desde el Dashboard, el usuario selecciona la opción Certificados.
3. El sistema presenta el módulo de consulta de extractos bancarios.
4. El usuario selecciona el mes que desea consultar.
5. El sistema valida la solicitud:
   1. Si el mes seleccionado no es válido (anterior a la creación de la cuenta), el sistema muestra un mensaje indicando que no hay extractos disponibles para ese período.
   2. Si la información es válida, el sistema solicita al generador de enlaces la creación de un enlace firmado temporal para el documento correspondiente. Si en un mes no hubo movimientos, de todas formas se genera un extracto que así lo certifique.
6. El generador de enlaces consulta el almacenamiento de documentos y crea un link firmado temporal con permisos de lectura.
7. El sistema devuelve el enlace firmado al usuario.
8. El navegador del usuario inicia automáticamente la descarga del archivo PDF correspondiente al extracto bancario del mes seleccionado.
9. El usuario puede guardar o visualizar el documento.
10. Una vez completada la descarga, el usuario puede regresar al Dashboard para continuar utilizando el sistema.


Flujo 6: Cierre de sesión
Objetivo: finalizar de forma segura la sesión del usuario.
1. Desde el Dashboard, el usuario selecciona la opción de cerrar sesión.
2. El sistema invalida la sesión activa.
3. El usuario es redirigido a la pantalla de autenticación.

4. Discusión y reflexión
Análisis del diseño
En esta entrega, se tomaron decisiones ordenadamente para alcanzar un diseño que cumpliera con las condiciones esperadas para nuestra billetera digital. El enfoque principal fue el diseño arquitectónico, pero también se cubrieron consideraciones primarias de diseño detallado.


En conjunto, se hizo el diseño del sistema en términos de las estructuras Componentes y Conectores (C&C) y de despliegue, los flujos funcionales y los recursos de nube que nos interesa usar.


Empezando con el estilo de arquitectura, cumplimos con plantear un híbrido que combine microservicios con arquitectura orientada a eventos; empezando por construir una vista C&C de microservicios e integrando de manera coherente los componentes esenciales de eventos (productor, canal y consumidor), implementando así el patrón del bus de eventos. Identificamos como uno de los insumos de información más importantes del sistema a los registros de transacciones: la finalización de una transacción es un evento que se debe comunicar a través del sistema, por tanto fue designado como el mensaje que viajará a través del canal, que a su vez conecta al microservicio donde se originan las transacciones con el componente que las almacena para el historial. Tomamos el bus de eventos de CocoCash —el canal— como un componente lógico en la estructura, y al plantearlo se aplican transitivamente los patrones de cola, bus de eventos, petición-respuesta asíncrona, abastecimiento de eventos y publicación-suscripción. 


Asimismo, al construir la vista C&C se tuvo en cuenta la organización por capa para ayudarnos a clarificar la jerarquía de componentes del sistema en relación a su cercanía con el usuario.
Por otro lado, se tiene que el estilo de microservicios es ideal para la nube debido a su naturaleza agnóstica, la flexibilidad e independencia para los desarrolladores [1].


Respecto a los patrones, se implementaron patrones de orquestación congruentes con el estilo de microservicios y cuya implementación es facilitada por la nube (API Gateway y balanceador de carga, en cuanto a patrones de orquestación). Se eligió también el patrón de redundancia activa (repuesto en caliente) por medio de las réplicas que tenemos de los microservicios: frontend, core de billetera, bus de eventos y el del historial de transacciones; en diferentes zonas de disponibilidad. La ventaja que ofrece este patrón aquí es mejorar la disponibilidad gracias a que las réplicas atienden el mismo flujo de solicitudes en paralelo (con failover automático, esencial para el negocio bancario que proponemos).


En cuanto a la capa de datos, se adoptó el patrón Database-per-Service, en el cual cada microservicio es dueño exclusivo de su persistencia [2]. Esta decisión reduce el acoplamiento estructural entre servicios y permite su evolución independiente, lo cual es coherente tanto con el estilo de microservicios como con los principios de diseño nativos de la nube [1]. Para los datos financieros que requieren consistencia fuerte (saldos) se eligió una base de datos relacional administrada en modo Multi-AZ, en la que se implementa un esquema de replicación activo-pasivo con conmutación automática por falla [3]. En términos prácticos, esto permite preservar la corrección transaccional del sistema y una conmutación por error automática en, por lo general, menos de 35 segundos, sin pérdida de datos y sin intervención manual [4]. Adicionalmente, estas bases de datos habilitan cifrado en reposo sobre el volumen de almacenamiento, las réplicas y los snapshots, necesario para datos financieros.


Para el historial de transacciones se utilizó una base de datos NoSQL administrada, ya que esta información se maneja como un registro de solo agregar: las transacciones no se modifican ni participan en lógica transaccional posterior, únicamente se consultan. Por lo tanto, decidimos separarla de la base relacional, cuya responsabilidad es mantener consistencia fuerte, mientras el historial de transacciones debe ofrecer disponibilidad y eficiencia de escritura. La base de datos cifra todos los datos en reposo por defecto usando AES-256, sin necesidad de configuración adicional. De esta manera, en la capa de datos se distingue explícitamente entre el estado actual del sistema (balance) y el registro de hechos ocurridos (bitácora de transacciones).


Desde la perspectiva de la computación en la nube, las decisiones arquitectónicas fueron tomadas considerando cómo las tecnologías seleccionadas pueden potenciar determinados atributos de calidad. A saber, el uso del API Gateway administrado permite escalar automáticamente a miles de solicitudes por segundo e incorpora mecanismos de throttling y autenticación integrados [5]; el bus de eventos basado en colas y notificaciones ofrece entrega durable, reintentos automáticos y retención de mensajes por varios días [6], esto otorga resiliencia ante fallos temporales de consumidores. Asimismo, los servicios serverless (como DynamoDB) escalan automáticamente en función de la carga, así se pueden manejar grandes volúmenes de eventos sin aprovisionar manualmente (facilita la escalabilidad) [7].
Para plantear los flujos funcionales del sistema, consideramos las funcionalidades esenciales que debe ofrecer CocoCash: iniciar sesión, transferir dinero a otra cuenta, consultar los movimientos y salir de forma segura. Esto con el fin de asegurar que el prototipo cumpla con las características que lo cataloguen como una billetera digital. Si bien el dashboard será el módulo funcional principal, donde se verá el saldo (por practicidad), decidimos también separar responsabilidades haciendo un módulo de transferencias, desde donde se enviará el dinero.


Por otra parte, en seguridad, la delegación de la autenticación a un proveedor especializado con mecanismo multifactorial (cognito) reduce el riesgo de errores de configuración de seguridad y vulnerabilidades asociadas con mecanismos de autenticación desarrollados internamente [8].  Un patrón de redes relacionado fue la segmentación en subredes: las zonas de disponibilidad de nube están divididas en subredes (unas públicas, otras privadas). Limitamos el acceso a nuestro sistema a nivel de despliegue, reduciendo la superficie expuesta que puede generar una vulnerabilidad (se reduce más cuando se usa también una red privada virtual, justo como diseñamos).
En confiabilidad, la replicación multi-zona de balanceadores, colas y bases de datos permite tolerar fallos de infraestructura completos disminuyendo la probabilidad de que el usuario perciba la interrupción. En mantenibilidad, evidentemente reducimos esfuerzos operativos al no tener que preocuparnos por los servidores (dado que es un sistema nativo de la nube), solamente nos encargamos del desarrollo, lo que otorga abstracciones más limpias, actualizaciones más rápidas y una ágil evolución a largo plazo del sistema. Finalmente, la interoperabilidad se ve favorecida (en su nivel sintáctico) por el uso de protocolos estándar (HTTP, REST, JWT, eventos JSON), lo cual permite a futuro que otros sistemas, plataformas y servicios intercambien datos y autentiquen interacciones con CocoCash sin necesitar una integración personalizada; por ejemplo, si llegamos a necesitar que las peticiones lleguen de distintos canales (i. e. página web, aplicación móvil, cajero).


Consideramos esta propuesta de solución como efectiva, ya que los atributos de calidad en CocoCash son una consecuencia directa del aprovechamiento intencional de sus capacidades cloud-native.
